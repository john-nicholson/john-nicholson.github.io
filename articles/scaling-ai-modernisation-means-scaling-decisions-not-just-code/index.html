Scaling AI Modernisation Means Scaling Decisions, Not Just Code

22 September 2026·2506 words·12 mins

There is a growing assumption in software modernisation that AI will allow us to industrialise the analysis and transformation of existing estates. Give a model a codebase, define the target architecture and increasingly it can analyse, refactor, generate tests and produce a substantial amount of the target implementation.

There is clearly value in that, but the idea becomes much harder when we move from an individual application to an enterprise estate. The problem is not simply that organisations use different technologies. There can be enormous variation between two applications built in the same language, by the same organisation and notionally against the same standards. Years of design decisions, local conventions, framework choices, technical debt, developer preferences and changing architectural standards leave each application carrying part of its own history.

That makes the idea of a single modernisation flow difficult. Even where the destination is common, the route to get there may not be.

The difficult part is the decision
#

Consider something that sounds relatively straightforward: an organisation wants to move its applications onto a common authentication authority.

At first glance, this looks like exactly the kind of repetitive change we should be able to automate. Identify the existing authentication implementation, replace it with the target mechanism, generate the necessary configuration and tests, and move on to the next application.

The reality is much more complicated. The estate may contain applications using different authentication patterns, different libraries and different generations of standards. Some applications may authenticate users directly, others may delegate authentication through another service, and still others may rely on authentication established somewhere upstream. There may be machine-to-machine identities, service accounts, token exchanges, legacy protocols and bespoke implementations accumulated over many years.

Even if the code transformation for each archetype can be automated, selecting the correct transformation requires context. Then there is another problem: sequence.

An application rarely exists alone. If one service changes its authentication mechanism while a dependent service still expects the previous identity or token model, a technically correct migration can still break the wider system.

The modernisation problem is therefore not just:

How do we change this application?

It is also:

What kind of application is this, what depends upon it, which migration path is appropriate, how confident are we in that classification, and when is it safe to make the change?

That is a very different problem from code generation.

Model the migration, not just the target
#

This is where I think some of the thinking we already apply to business value streams becomes useful in technology modernisation.

If this were a deployment or continuous-delivery problem, we would already be inclined to map the value stream. We would look at where work waits, where approvals happen, where environments constrain flow, where testing becomes a bottleneck and where hand-offs introduce delay or risk.

Modernisation should be treated the same way.

In fact, I would argue the need is greater because the system is often operating across a transitional architecture rather than a steady-state one. Existing applications, target platforms, temporary integration patterns, shared environments and different migration waves all coexist for a period of time. That creates constraints which are easy to overlook if the modernisation programme is viewed primarily as a code-transformation exercise.

Rather than defining a single prompt or transformation pipeline and applying it repeatedly, we can model the migration states and the decisions required to move between them.

For an authentication migration, for example, the organisation might identify a number of recurring archetypes across the estate. Each archetype can have known preconditions, transformation patterns, validation requirements and dependencies that must be satisfied before it is allowed to progress.

A conceptual modernisation flow might look like this:

flowchart LR
    A[Discover] --> B[Classify]
    B --> C[Dependency Analysis]
    C --> D[Select Migration Pattern]
    D --> E[Transform]
    E --> F[Validate]
    F --> G[Release]
    G --> H[Observe]

    X[(Enterprise Context)]
    X -.-> A
    X -.-> B
    X -.-> C
    X -.-> D
    X -.-> E
    X -.-> F
    X -.-> G
    X -.-> H

The important part is that each transition can have an explicit decision associated with it.

What evidence is required before an application can be classified? How confident must the system be before it is allowed to select a migration pattern? What dependencies have to be migrated first? Which tests demonstrate that the change has preserved the required behaviour? At what point does a human need to intervene?

Once those decisions are explicit, we can start asking a much more useful question about AI.

Not simply “Can AI perform the migration?”, but “What authority should we give each agent at each point in the migration?”

Faster code can still create slower flow
#

This is where I think a lot of modernisation thinking risks falling into the same trap that delivery teams have been trying to remove for years.

If we optimise only the transformation step, we may make one part of the system significantly faster while the rest of the flow remains constrained. The result is not necessarily faster delivery. It may simply be more work in progress.

A simplified current-state flow often looks something like this:

flowchart LR
    A[Applications Identified] --> B[AI / Engineering Analysis]
    B --> C[Code Changes Produced]
    C --> D[Human Review]
    D --> E[Test Environment]
    E --> F[Integration Testing]
    F --> G[Architecture / Security Approval]
    G --> H[Release]

    D -. WIP builds .-> D
    E -. Environment constraint .-> E
    F -. Dependency failures .-> F
    G -. Approval queue .-> G

If AI makes the analysis and code-production steps dramatically faster, but human review, test environments, integration testing and approvals remain fixed, then the system simply pushes more change into the constrained parts of the flow.

That is why the transitional constraints around testing and environments need to be front and centre rather than treated as downstream delivery concerns. They do not go away because AI can produce more code. If anything, they become more important because the rate at which change can be generated increases.

The modernisation problem is therefore not simply one of producing transformation capacity. It is one of managing flow across the entire migration system.

Autonomy should vary through the flow
#

Not every decision deserves the same level of autonomy.

An agent might have complete authority to inspect repositories, identify frameworks, build dependency information and compare an application against known migration archetypes. There may be little value in requiring human approval for every one of those activities.

The same agent might then recommend a migration route with an associated confidence level. For a well-understood pattern with strong evidence and comprehensive automated testing, the organisation may allow the transformation to proceed automatically. For an unusual implementation, low-confidence classification or particularly critical application, the decision may be escalated to an engineer or architect.

That creates a spectrum of agency rather than a binary choice between manual delivery and fully autonomous AI.

More importantly, the decision about autonomy is made deliberately. It becomes part of the architecture of the modernisation system rather than something implied by whichever AI tooling happens to be used.

A simple way of thinking about that is:

flowchart LR
    A[Known Archetype
Strong Dependency Data
High Test Coverage] --> B[High Confidence]
    B --> C[Greater Agent Autonomy]

    D[Unusual Pattern
Weak Dependency Data
Limited Tests] --> E[Low Confidence]
    E --> F[Human Decision Required]

The objective is not maximum autonomy. It is the highest level of autonomy that the available evidence can justify.

Transitional architecture is where the risk lives
#

Modernisation programmes rarely move cleanly from an old state to a new one. For months or years, organisations operate across both.

That means the migration system has to understand not just the target architecture, but the transitional architecture: which components have moved, which have not, which interfaces remain backward-compatible, which environments are shared, which tests are available and which temporary controls are currently keeping the whole thing together.

This matters particularly for authentication, because identity is rarely isolated to one application. A service may issue tokens consumed elsewhere, depend on another system for user context, or be part of a chain where different components move at different times. Changing one application correctly can still break the overall flow if the transition sequence is wrong.

For example:

flowchart LR
    A[Application A
Issues Token] --> B[Application B]
    A --> C[Application C]
    C --> D[Application D]
    C --> E[Application E]

All five applications may be individually suitable for transformation. That does not mean they can be migrated independently.

The migration sequence is constrained by the relationships between them.

The same applies more broadly across data, integration, networking, runtime platforms and deployment pipelines. That is why testing and environments have to be treated as part of the migration decision itself. If a test environment cannot accurately represent a transitional state, or if multiple applications must move together because of a dependency chain, that is part of the modernisation model.

The agentic system needs to reason about those constraints before transformation, not discover them after code has already been generated.

Enterprise context changes what an agent can know
#

This is where a semantic understanding of the wider estate becomes particularly important.

A coding agent operating against one repository can understand a surprising amount about that repository. What it cannot easily understand is everything that exists outside it: which other systems call the application, which business capabilities depend upon it, who owns it, what runtime constraints apply, which architectural decisions govern it, and what other migrations are already underway.

At enterprise scale, that context can be as important as the code itself.

A knowledge graph or equivalent semantic model can represent relationships between applications, APIs, identities, infrastructure, teams, business capabilities and architectural standards. The agent examining an authentication implementation no longer sees merely a library that needs replacing; it can understand where the application sits within a wider dependency chain.

This is where scaling the semantic knowledge of the estate becomes particularly powerful. The organisation is no longer relying on each agent to rediscover the estate one repository at a time. Instead, agents can reason against a shared enterprise context that captures both technical and organisational relationships.

The code is only part of the truth.

Agents need different responsibilities
#

This also suggests that a modernisation system should probably not be thought of as one enormously capable coding agent.

Different agents can operate against different parts of the problem. One may specialise in estate discovery and classification, another in dependency analysis, another in selecting transformation patterns, and another in generating or modifying code. Validation agents can examine tests, architecture conformance, security controls and behaviour, while orchestration coordinates the progression of an application through the migration flow.

The important thing is not the number of agents. It is that their responsibilities, evidence and decision rights are explicit.

That makes the system considerably easier to reason about than asking a general-purpose agent to inspect an application and “modernise it”.

It also gives us a much stronger basis for trust. If an agent selects migration pattern three, we should be able to understand why. Which characteristics of the application caused that classification? Which dependencies were considered? Which architectural rules were applied? What evidence gave the system sufficient confidence to proceed?

The interesting output of the system is therefore not simply transformed code.

It is a traceable chain of decisions that resulted in that code being transformed.

Scaling confidence alongside delivery
#

This becomes particularly important when organisations try to industrialise modernisation.

If we accelerate code generation without accelerating our ability to understand and validate the decisions surrounding it, we simply move the bottleneck. Engineers and architects become responsible for reviewing an increasingly large volume of AI-generated change, and eventually the human-in-the-loop becomes the constraint.

This is also where the discussion about dark factories becomes more useful.

There is an understandable attraction to the idea of a largely automated software delivery system where agents can analyse, change, test and deploy software with minimal human intervention. But autonomy should not be treated as the objective in itself.

The real objective is confidence sufficient to justify autonomy.

A dark factory is only valuable if the organisation understands why the system is allowed to proceed. That confidence cannot come from code-generation quality alone. It has to come from the surrounding evidence: known migration archetypes, validated dependency models, reliable tests, architecture policies, environment readiness, security controls and clear rules about where human judgement is still required.

In that sense, modelling the modernisation value stream is not separate from the dark-factory ambition. It is what makes it credible.

The more explicitly we can describe the migration states, decision rights, evidence and constraints, the more safely we can increase autonomy. A well-understood migration pattern with strong automated testing and no unresolved dependency risk might move almost entirely through an automated path. An unusual application with weak test coverage, undocumented dependencies or a shared legacy environment should not.

That is not a failure of automation. It is the system correctly expressing uncertainty.

Known archetypes, deterministic rules, automated tests, architecture policies, semantic dependency information and AI reasoning can collectively provide evidence for a decision. Where that evidence is strong, the system can progress with greater autonomy. Where it is incomplete, contradictory or unusual, humans become involved because their judgement actually adds value.

This is the same principle that applies more broadly to agentic systems: use deterministic automation where the answer is known, reasoning where interpretation is required, and human judgement where accountability or genuine ambiguity remains.

Modernisation becomes an adaptive flow
#

Seen this way, AI changes modernisation in a more interesting way than simply making developers faster.

We can begin to model the estate, model the migration routes through it and model the decisions required to move applications between states. Agents can discover, classify, reason and act against that model, while deterministic automation handles the repeatable transformations and validations that we already understand well.

As the programme progresses, the system can learn more about the estate. New archetypes can emerge. Migration patterns can be refined. Exceptions encountered in one application can inform how the next hundred are assessed. The enterprise model becomes richer rather than each migration beginning again with an empty context window.

That is where I think the opportunity starts to become much larger than AI-assisted coding.

The goal is not a machine that can rewrite every application in the estate. It is a modernisation system that understands what should change, why it should change, which path it should follow, when it is safe to change, what constraints surround that change and where human judgement still matters.

If we already use value-stream mapping to understand deployment and continuous delivery, we should apply the same discipline to modernisation. The difference is that the modernisation value stream has to account for much more than the software change itself: dependencies, sequencing, temporary architecture, environments, testing, decision rights and confidence.

AI can accelerate the flow dramatically.

But the real advantage comes when we can also explain why the flow is safe to accelerate.

That is the point at which modernisation starts to become not only faster, but genuinely scalable.
