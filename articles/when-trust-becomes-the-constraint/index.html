When Trust Becomes the Constraint

13 September 2026·1667 words·8 mins

One of the more difficult problems I keep coming back to with AI-assisted software modernisation isn’t really a technology problem. It’s trust.

We have all seen an LLM confidently make something up, merge two facts that happened to look similar, or produce an explanation that sounds entirely reasonable until someone who really understands the domain reads it. Once you have seen that happen a few times, it changes how you approach the capability, and that matters when we start asking AI to help modernise software.

The obvious response is control. If we don’t completely trust the generated code, we review it. If we don’t completely trust the generated specification, we review that too. Perhaps we generate a specification from the legacy application, have somebody approve it, generate new code from the approved specification, generate tests, review those, and then put the normal release controls around the resulting system.

Individually, every one of those steps is reasonable. Collectively, though, there is a risk that we recreate exactly the sort of delivery pipeline we have spent the last decade trying to simplify.

Moving the bottleneck
#

There is a familiar pattern here from software delivery. When release processes were slow, organisations often responded by adding more people to release management, more coordination, more checklists and more approvals. Sometimes that helped. Sometimes it simply made the process around the constraint larger without really changing the constraint itself.

AI modernisation can create a similar problem.

Imagine using AI to analyse a large legacy estate and generate detailed specifications for thousands of components. The generation itself may be extraordinarily fast, but somebody still has to decide whether the output is good enough to act on.

If every generated specification has to be read and approved before we trust it, then the AI may have created work faster than the organisation is capable of consuming it. The bottleneck has not disappeared; it has shifted from producing the specification to verifying it.

That starts to change the economics of the approach.

We can put humans in the loop at every stage: specification, design, code, tests and release. That may reduce some forms of risk, but it can also absorb much of the time advantage we hoped to gain in the first place.

I’ve written previously about the tendency to add human approval when what we really need may be a better guardrail. The same tension shows up here. The issue is not that review is unnecessary. It is that we need to be clearer about what the review is intended to establish.

Code-to-code isn’t necessarily modernisation
#

There is another temptation here. If generating and reviewing specifications becomes expensive, why not simply transform the old code directly into new code?

That can work technically, but modernisation usually exists because something about the old system no longer fits the environment in which it needs to operate.

Legacy systems accumulate assumptions: architectural patterns suited to older deployment models, batch processes that made sense when compute was scarce, tight coupling that evolved over years, interfaces shaped around organisational boundaries that no longer exist, and business rules mixed with implementation detail.

A sufficiently capable model may be able to translate that faithfully from one language or framework into another. The difficulty is that fidelity is not always the goal.

A highly accurate code-to-code transformation can still preserve the architectural and design decisions that made the system difficult to operate in the first place. The syntax is modern, but the system may not really be.

In some ways, this creates an uncomfortable trade-off. The more freedom we give the AI to reinterpret what the legacy application was actually trying to achieve, the more useful its judgement may become. At the same time, the more freedom we give it, the less deterministic the result becomes, and the harder it is to establish confidence in the output.

The constraint may be trust
#

This is where I think the problem becomes more interesting.

Perhaps the main constraint in AI-enabled modernisation is not generation capacity at all. Perhaps it is trust.

A client may not fully trust the AI-generated output. A delivery team may, in some cases, trust it too readily, particularly when the model is operating in a part of the domain where they are less experienced themselves. Both responses are understandable, and both carry risk.

Low trust tends to create gates, approvals and verification. Excessive trust creates the possibility of accepting something because it is plausible rather than because it is correct.

Our traditional delivery mechanisms are not especially well suited to this tension. Software systems have generally been treated as deterministic things: given the same input and the same state, we expect broadly the same behaviour.

Large language models are different. They are probabilistic systems that can exhibit something closer to judgement than traditional software, and that changes the nature of the control problem.

I increasingly wonder whether some of the difficulty we have applying AI inside organisations comes from trying to operate a non-deterministic capability using control mechanisms designed for deterministic systems.

What are we actually reviewing?
#

That raises a more fundamental question about what we are trying to validate.

Our instinct is usually to validate the artefact: read the specification, review the code, check the generated tests, approve the document.

But an AI-assisted modernisation system is not just the model. The effective system is something closer to:

model + context + memory + tools + constraints + evaluation

Change the context and the behaviour changes. Change the available memory and the behaviour changes. Change the retrieval strategy, system instructions or tools and the behaviour changes again.

If that is the real system, validating thousands of individual documents may not always be the most useful level of abstraction.

We don’t normally gain confidence in a compiler by manually reviewing every line of machine code it generates. AI is not equivalent to a compiler, of course, and its non-determinism is exactly what makes this harder. But there may still be something useful in the comparison.

Rather than asking only whether every generated specification is correct, perhaps we should also be asking how well the system understands the application.

That shifts the nature of assurance.

Can it explain why a particular business rule exists? Can it identify contradictions between implementations? Can it trace a behaviour from interface through application logic into data? Can it distinguish an implementation detail from genuine business intent? Can it show what evidence led it to a conclusion? Can an expert challenge that conclusion and see whether the underlying understanding holds up?

This starts to look less like document review and more like testing the quality of the system’s understanding.

Interviewing understanding
#

That language feels unusual when applied to software, but perhaps that is useful in itself.

If the real value of these systems is their ability to reason across large amounts of messy context, then evaluating them only through generated documents may not tell us enough about whether that reasoning is sound.

Take a legacy trading platform as an example. Rather than generating a 900-page specification and asking somebody to approve it from beginning to end, the modernisation team might interrogate the system’s understanding of the estate.

Which business capabilities appear to be critical? Which calculations are repeated across multiple implementations? Where are the contradictory rules? Which behaviours appear intentional and which look like implementation artefacts? What happens if a particular upstream feed is unavailable? Where else does this concept appear? What evidence supports this interpretation?

That is a different kind of interaction. It gives experienced people the opportunity to test relationships, assumptions and reasoning, rather than simply proofreading a very large body of generated text.

For me, that feels closer to the way trust may need to develop.

Guardrails and judgement
#

There is still an important tension here.

The more tightly we constrain these systems, the more predictable they become. That is useful, but beyond a point the same constraints can also reduce the judgement that made the AI useful in the first place.

If we force the model to perform only deterministic transformations, we can probably make the output easier to verify. We may also reduce the capability to little more than a sophisticated translation engine.

Modernisation often needs more than translation. It may require recognising that two differently named things are really the same business concept, noticing that a technical implementation no longer reflects the way the organisation operates, distinguishing an architectural constraint from an accident of history, or deciding that something should not be carried forward at all.

Those are judgement calls, and they are harder to express through simple binary controls.

So the goal may not be to remove non-determinism entirely. It may be to become much more deliberate about where it is useful, where it is acceptable, and how we build confidence around it.

A different operating model
#

That is why I think the more interesting question around AI modernisation is becoming less about the model itself and more about the operating model around it.

There will still be places where deterministic behaviour matters, places where individual outputs need to be checked, and places where traditional controls remain entirely appropriate.

But there may also be places where confidence comes from something broader: the quality of the context, the traceability of conclusions, the ability to challenge the system’s reasoning, and the consistency of its understanding across a wider body of evidence.

That makes trust less of a single approval decision and more of something that has to be designed into the system.

AI can generate code extraordinarily quickly. It can generate documentation even faster. Neither matters very much if the organisation cannot build enough confidence in the result to act on it.

If trust is the real constraint, generating more artefacts probably will not solve it. The harder question is how we design the technical and organisational system around the AI so that trust can develop without recreating the very bottlenecks we were trying to remove.
