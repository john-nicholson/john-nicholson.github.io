From Coding Agents to Loop Engineering: Building Engineering Memory for AI

14 September 2026·3048 words·15 mins

Most AI coding setups still look suspiciously like a faster version of the way we have always developed software. A developer asks for a change, an AI model explores some files, writes some code, perhaps runs a few tests, and returns the result. Add more specialised agents and the flow becomes more sophisticated — an architect creates a plan, an explorer inspects the repository, a developer implements the change and a reviewer checks the result — but fundamentally it is still a pipeline.

I think the more interesting shift is to stop treating AI-assisted development as a sequence of activities and instead design it as a closed engineering loop. The distinction matters. Rather than asking an agent to implement a change, ask the engineering system to reach a desired state and produce enough evidence that it has done so. Once you take that seriously, the architecture changes quite quickly, because the system needs more than tools and context. It needs persistent engineering memory.

As I have been working through this locally, that has also changed how I think about the role of the knowledge graph. I still think the graph is important, but it is not the whole answer. What we really need is a persistent model that joins intent, architecture, source code, evidence, history and semantic context, and allows agents to interrogate that model in different ways depending on the problem they are trying to solve.

From pipeline to engineering loop
#

My current local coding environment already uses a set of specialist roles around OpenCode: Architect, Explorer, Developer, Reviewer and Documenter. The obvious first architecture looks like this:

flowchart LR
    A[Intent] --> B[Architect]
    B --> C[Explorer]
    C --> D[Developer]
    D --> E[Reviewer]
    E --> F[Documenter]

There is nothing particularly wrong with that model, but it has an obvious limitation: the process has an end. If the reviewer identifies a problem, we generally rely on another prompt or another human action to restart the process. That feels like the wrong abstraction. A stronger model is a feedback loop.

flowchart TD
    A[Intent / Requirement] --> B[Architect]
    B --> C[Explorer]
    C --> D[Developer]

    D --> E[Deterministic Verification]
    D --> F[Semantic Review]

    E --> G[Evidence]
    F --> G

    G --> H{Desired state evidenced?}

    H -- No --> I[Reason about gap]
    I --> C

    H -- Yes --> J[Document / Curate]
    J --> K[Engineering Memory]
    K --> B

The core cycle becomes Intent → change → observe → compare → reason → change. That is not a new idea in engineering. It is the same feedback principle that underpins DevOps, continuous delivery and most mature engineering systems. The difference is that we are now making that loop explicit for AI and giving the agents enough persistent context to reason across iterations rather than rebuilding their understanding every time.

Engineering against a desired state
#

Consider a simple request: “Add authentication.” A conventional coding agent may interpret that primarily as an implementation task, but a loop-oriented engineering system should first turn it into a desired state.

Capability:
  Authenticated access

Constraints:
  OAuth/OIDC
  Microsoft Entra
  No credentials stored locally

Acceptance:
  Unauthenticated requests are rejected
  User identity is propagated downstream
  Role policies are enforced
  Automated tests demonstrate all three

That changes the nature of the work. The developer is no longer simply trying to generate plausible authentication code; the engineering loop is trying to make the observed state of the software satisfy these conditions. After implementation, the useful output may look more like this:

Build                 PASS
Unit tests            PASS
Integration tests     FAIL
Security checks       PASS
Architecture checks   PASS

The failed integration test is not simply an error message. It is evidence that the desired state has not yet been reached, and that evidence should drive the next iteration.

The missing piece is persistent understanding
#

Once you model development this way, another problem becomes obvious: how does each agent understand the software system? Today, most coding agents repeatedly reconstruct context from source files, README files, architecture notes, Git history, search results, the current prompt and whatever still fits inside the context window. This works surprisingly well, but much of the system model remains implicit and every agent is rebuilding some version of the same understanding.

My first instinct was to solve that with a knowledge graph. I still think that is part of the answer, but only part. A graph is extremely good at answering questions such as “what implements this requirement?”, “which tests verify this capability?” or “what components depend on this service?”, but not every form of engineering memory is naturally graph-shaped.

Test runs, build history, execution times, commits and observations are often relational. Documentation and source fragments benefit from semantic similarity. Architecture decisions need both structured identity and rich textual context. Git remains uniquely good at recording authored change over time. The better architecture is therefore not simply a graph for coding agents, but an engineering memory system with several complementary ways of understanding the same estate.

The graph still matters
#

A basic code graph might tell us:

AuthController
    CALLS
AuthService

Useful, but relatively low-level. What I want the engineering graph to represent is the chain between business intent and observable engineering evidence.

flowchart TD
    R[Requirement]
    C[Capability]
    S[Service / Component]
    CODE[Code]
    ADR[Architecture Decision]
    T[Test]
    E[Evidence]

    R -->|SATISFIED_BY| C
    C -->|REALISED_BY| S
    S -->|IMPLEMENTED_BY| CODE

    S -->|CONSTRAINED_BY| ADR

    R -->|VERIFIED_BY| T
    T -->|PRODUCES| E

Other relationships can sit alongside these:

Component DEPENDS_ON Component
API EXPOSES Capability
Change MODIFIES Component
Incident CAUSED_BY Component
Test VERIFIES Requirement
ADR CONSTRAINS Component

Now an agent is no longer just navigating files. It can reason about the relationship between intent, implementation and evidence. That is where the graph earns its place, but it should be one view of engineering memory rather than the entire storage model.

From graph database to multi-model engineering memory
#

My initial design was to keep an authored representation in Git, load it into a graph database, and let the agents interrogate that runtime graph.

flowchart LR
    GIT[Git] --> JSON[Graph files]
    JSON --> GRAPH[(Graph Database)]
    GRAPH --> AGENTS[Agents]

It is elegant, but it starts to look too narrow once you consider what the system actually needs to remember. There are several different classes of engineering knowledge.

flowchart TD
    A[Intentional Knowledge]
    B[Structural Knowledge]
    C[Historical Evidence]
    D[Semantic Context]

    A --> M[Engineering Memory]
    B --> M
    C --> M
    D --> M

Intentional knowledge includes requirements, capabilities, architecture decisions and explicit constraints. Structural knowledge includes imports, calls, dependencies, APIs, schemas and relationships discovered from code. Historical evidence includes builds, tests, deployments, failures, observations and changes over time. Semantic context includes documents, code chunks, incidents and concepts that may be related even where no explicit relationship has yet been established.

Trying to force all of that into one graph representation is possible. I am no longer convinced it is desirable.

PostgreSQL as the engineering memory foundation
#

The architecture I am now leaning towards uses PostgreSQL as the foundation, with different models layered over it.

flowchart TD
    G[Git / Authored Intent]
    S[Source Code]
    R[Runtime & CI Evidence]

    I[Engineering Memory Ingestion]

    PG[(PostgreSQL)]

    REL[Relational State]
    AGE[Apache AGE
Graph]
    VEC[pgvector
Semantic Similarity]
    FTS[Full Text Search]

    CTX[Context Builder]
    A[OpenCode Agents]

    G --> I
    S --> I
    R --> I

    I --> PG

    PG --> REL
    PG --> AGE
    PG --> VEC
    PG --> FTS

    REL --> CTX
    AGE --> CTX
    VEC --> CTX
    FTS --> CTX

    CTX --> A

This feels like a better fit because each mechanism can be used where it is strongest. Normal PostgreSQL tables handle structured engineering state and evidence. Apache AGE provides graph traversal over explicit relationships. pgvector provides fuzzy semantic retrieval. PostgreSQL full-text search handles lexical discovery. Git remains the durable record of authored intent and source history.

The important bit is that the agents do not need to care which mechanism answered the question. They need a useful, bounded context.

Different questions need different retrieval models
#

This becomes obvious when you look at the types of questions an engineering agent actually asks. Graph traversal is ideal for questions such as “what implements this requirement?”, “what depends on this component?”, “which ADR constrains this service?” or “which tests verify this capability?”. Relational queries are better for “which tests failed after this commit?”, “what was the duration of the last ten builds?”, “when was this component last changed?” or “which evidence was collected for this requirement?”.

Semantic retrieval helps with a different class of question again: “have we seen a similar failure before?”, “which architecture decisions appear relevant to this problem?” or “what other parts of the estate discuss the same business concept?”. And ordinary text search remains extremely useful for finding an ADR by number, locating references to a service, or finding the configuration containing an endpoint.

The interesting capability is not choosing one retrieval model. It is composing them.

The context builder becomes the important boundary
#

That changes one part of the architecture quite significantly. Earlier, I imagined a small graphctl utility sitting in front of the graph database. I still like the idea of a stable interface, but its responsibility is now broader than graph access. Call it graphctl, engmem, or something else; the name matters less than the abstraction.

An agent might ask:

explain test:T92

The engineering-memory layer could then perform several operations:

flowchart TD
    Q[Explain Test T92]

    SQL[SQL
Latest failure & history]
    G[AGE
Requirement & component relationships]
    V[pgvector
Similar failures / ADRs]
    H[Git
Recent changes]

    C[Bounded Context]

    Q --> SQL
    Q --> G
    Q --> V
    Q --> H

    SQL --> C
    G --> C
    V --> C
    H --> C

The resulting context might say that T92 verifies R127, R127 is satisfied by capability C14, C14 is primarily implemented by S7 and S9, S7 changed in the current commit, the test was passing before that change, a previous incident involving missing identity claims affected the same component, and ADR-017 defines the expected identity mechanism.

That is a very different starting point from “here is the repository, a test failed, work it out.” The value of the memory layer is that it turns a large search problem into a bounded reasoning problem.

The Architect manages desired state
#

This also changes the role of the Architect agent. Rather than producing an implementation plan and disappearing, the Architect can define the desired engineering state. Imagine asking: “Add Xero integration.”

The existing model may describe:

Financial Reporting
 ├── Bank data
 ├── Donations
 └── Budgeting

The desired state may introduce:

Financial Reporting
 ├── Bank data
 ├── Donations
 ├── Budgeting
 └── Xero Integration
       ├── OAuth lifecycle
       ├── Tenant mapping
       ├── Account mapping
       ├── Transaction import
       └── Reconciliation rules

The work becomes a transformation:

flowchart LR
    A[Current State]
    B[Desired State]
    C[Delta]
    D[Implementation]
    E[Observed Evidence]

    A --> B
    B --> C
    C --> D
    D --> E

The important part is that the desired state is persistent. The developer, verifier and reviewer are all working against the same model rather than a series of loosely connected prompts.

Explorer becomes a curator of understanding
#

Explorer then becomes responsible for keeping engineering memory aligned with reality. Some relationships can be discovered deterministically: imports, function calls, package dependencies, API routes, database schemas, infrastructure resources, tests and pipelines. Others require inference.

For example:

TrusteeService
    IMPLEMENTS
Trustee Eligibility

That may not be directly represented anywhere in the source. An LLM may infer it from names, behaviour, documentation and surrounding context. That distinction matters, so every assertion should carry some notion of source and provenance.

{
  "from": "svc:trustee-service",
  "type": "IMPLEMENTS",
  "to": "cap:trustee-eligibility",
  "source": "explorer",
  "provenance": "src/services/TrusteeService.ts",
  "confidence": 0.91
}

A relationship derived from an AST, a relationship explicitly authored by an architect, and a relationship inferred by a model should not silently carry the same authority. Engineering memory needs to know not just what it believes, but why it believes it.

pgvector is not just there for RAG
#

This is one of the parts I find particularly interesting. It is easy to think about vector search purely as a mechanism for feeding documents into an LLM, but in this architecture its role is broader.

The graph describes relationships we have explicitly established:

AuthService
    IMPLEMENTS
Authentication

Vector similarity helps us discover relationships that may exist:

Identity federation ADR
Missing claims incident
SSO requirement
Authentication implementation

That gives us a useful flow:

flowchart LR
    V[Semantic Similarity]
    I[Agent Inference]
    A[Candidate Assertion]
    E[Evidence]
    G[Established Graph Relationship]

    V --> I
    I --> A
    A --> E
    E --> G

The probabilistic mechanisms help us discover possibilities. Evidence and deliberate engineering decisions determine which of those possibilities deserve to become durable relationships. That pattern mirrors the broader principle behind the entire architecture.

Git remains important, but it does not contain everything
#

I still think Git should contain the things the engineering team deliberately asserts: requirements, ADRs, architecture definitions and perhaps explicit semantic relationships.

engineering/
├── requirements/
├── capabilities/
├── adr/
├── architecture/
└── relationships/

What I would no longer do is try to serialise the entire operational graph back into Git. There will eventually be far too much derived state: function relationships, embeddings, historical test results, build evidence, observations, confidence scores and agent discoveries. Persisting all of that as source-controlled JSON would create noise and duplicate information that can be derived again.

Git therefore remains an authoritative source, but not the only source.

flowchart TD
    G[Git
Intent & Source History]
    P[(PostgreSQL
Operational Engineering Memory)]
    R[Runtime
Observed Reality]
    L[LLM
Working Memory]

    G --> P
    R --> P

    P --> L
    L --> P

The distinction is useful: LLM context is working memory. PostgreSQL is operational engineering memory. Git is authored and historical record. Runtime and verification provide observed reality. None of those should be confused with the others.

Do not rebuild the memory every time
#

This also changes the startup model. When I was treating the graph database as a projection of Git, rebuilding it on startup seemed reasonable. With engineering memory, that no longer makes sense because historical observations are part of the value.

We want to be able to ask when a dependency first appeared, whether a failure has happened before, whether a test is historically flaky, what the architecture looked like when a decision was made, or which commit introduced a particular behaviour. The database should therefore persist across sessions and accumulate useful engineering context over time.

Startup becomes incremental:

flowchart TD
    A[Start Environment]
    B[Start PostgreSQL]
    C[Check Extensions / Migrations]
    D[Compare Indexed Commit to HEAD]
    E[Analyse Changed Files]
    F[Update Relationships]
    G[Refresh Embeddings Where Required]
    H[OpenCode Ready]

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F
    F --> G
    G --> H

That is much closer to the mental model of an experienced engineer joining a long-running product than an agent waking up with amnesia every time a new conversation starts.

Debugging becomes graph-guided, evidence-backed and semantically assisted
#

Consider again a failing test. Without engineering memory, the agent gets:

Test T92 failed.

and now has to search.

With engineering memory:

flowchart TD
    T[Test T92]
    R[Requirement R127]
    C[Capability C14]
    S[Service S7]
    CH[Recent Commit]
    ADR[ADR-017]
    INC[Similar Previous Incident]

    T -->|VERIFIES| R
    R -->|SATISFIED_BY| C
    C -->|IMPLEMENTED_BY| S
    CH -->|MODIFIED| S
    S -->|CONSTRAINED_BY| ADR
    INC -. semantically related .-> T

Now the agent can begin with the knowledge that T92 verifies requirement R127, R127 is implemented primarily by S7 and S9, S7 changed in the latest commit, ADR-017 constrains its identity behaviour, and a previous incident involving missing claims has strong semantic similarity to this failure.

That is not simply better retrieval. It is a fundamentally better reasoning environment.

The agents become responsibilities rather than separate models
#

At this point I would describe the system in terms of six responsibilities, not necessarily six separately running models.

Architect — intent: defines requirements, constraints, architecture decisions and desired state.
Explorer — understanding: continuously hydrates and challenges engineering memory against the actual software.
Developer — action: changes software, infrastructure and configuration.
Verifier — observation: executes deterministic tests, builds, scans and checks.
Reviewer — judgement: asks whether the collected evidence demonstrates the intended outcome without violating architectural constraints.
Documenter / Curator — memory: turns useful learning into durable engineering context.

Around those sits an orchestrator:

while desired_state != evidenced_state:
    determine_next_action()
    execute()
    collect_evidence()
    update_engineering_memory()
    evaluate_difference()

That loop obviously needs boundaries: iteration limits, cost controls, permissions, escalation points and clear rules about which actions an agent is allowed to perform autonomously. The point is not to build an infinitely autonomous developer. The point is to build a controlled engineering system that can continue working towards a desired state, while making its evidence and decisions visible.

Start smaller than the architecture diagram suggests
#

It would be easy to turn this into a platform project before proving that the loop itself is useful. I would start with PostgreSQL, a small relational schema for requirements and evidence, Apache AGE for a limited set of explicit relationships, pgvector for semantic retrieval, and a thin context-building interface for the agents. The first implementation only needs to connect one requirement to the components that realise it, the tests that verify it and the evidence produced by a run.

Then prove one loop.

flowchart TD
    A[Architect defines desired state]
    B[Engineering memory records intent]
    C[Developer changes source]
    D[Explorer updates understanding]
    E[Verifier runs checks]
    F[Evidence enters memory]
    G[Reviewer evaluates state]
    H{Satisfied?}

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F
    F --> G
    G --> H

    H -- No --> C
    H -- Yes --> I[Document and curate]

Only after that loop works would I expand the ontology, automate more ingestion, add richer semantic discovery or introduce more elaborate orchestration. The database architecture matters, but the value is in the behaviour it enables.

The bigger idea
#

What I find interesting is that this is converging on the same architecture I keep arriving at when thinking about enterprise AI. In the enterprise context: ontology + context + deterministic systems + AI reasoning + agents + memory. In a software engineering environment: engineering memory + deterministic tools + AI reasoning + specialist responsibilities + observed evidence. They are expressions of the same principle.

AI should not own truth. It should reason over a structured representation of truth, act through controlled mechanisms, observe the result, and continuously reconcile its model with reality.

That may turn out to matter more than simply giving coding agents larger models or larger context windows. The interesting evolution is not just from coding assistant to coding agent. It is from coding agent to engineering system.
