From Coding Agents to Loop Engineering: Using Knowledge Graphs to Build Better AI Engineering Systems

14 September 2026·2176 words·11 mins

Most AI coding setups still look suspiciously like a faster version of the way we have always developed software. A developer asks for a change, an AI model explores some files, writes some code, perhaps runs a few tests, and returns the result. Add more specialised agents and the flow can become more sophisticated — an architect creates a plan, an explorer inspects the repository, a developer implements the change and a reviewer checks the result — but it is still essentially a pipeline.

The more interesting question is what happens when we stop thinking about AI-assisted development as a sequence of activities and instead treat it as a closed engineering loop. The shift is subtle but important: don’t ask an agent to implement a change; ask the engineering system to reach a desired state and produce evidence that it has done so. That changes the architecture quite considerably.

From pipeline to engineering loop
#

My current local coding environment already uses a set of specialist roles around OpenCode: Architect, Explorer, Developer, Reviewer and Documenter. At first glance, the natural design looks like this:

flowchart LR
    A[Intent] --> B[Architect]
    B --> C[Explorer]
    C --> D[Developer]
    D --> E[Reviewer]
    E --> F[Documenter]

There is nothing wrong with this, but it has an obvious limitation: the process has an end. If the reviewer identifies a problem, we usually rely on another prompt or another human action to restart the process. A stronger model is a feedback loop.

flowchart TD
    A[Intent / Requirement] --> B[Architect]
    B --> C[Explorer]
    C --> D[Developer]

    D --> E[Deterministic Verification]
    D --> F[Semantic Review]

    E --> G[Evidence]
    F --> G

    G --> H{Desired state evidenced?}

    H -- No --> I[Reason about gap]
    I --> C

    H -- Yes --> J[Document / Curate]
    J --> K[Engineering Memory]
    K --> B

The core cycle becomes Intent → change → observe → compare → reason → change. That is not particularly exotic; it is the same feedback principle that underpins DevOps, continuous delivery and most mature engineering systems. What changes is that we make the loop explicit for AI.

Engineering against a desired state
#

Consider a simple request: “Add authentication.” A conventional agent may interpret that as an implementation task, but a loop-oriented system should first turn it into a desired state.

Capability:
  Authenticated access

Constraints:
  OAuth/OIDC
  Microsoft Entra
  No credentials stored locally

Acceptance:
  Unauthenticated requests are rejected
  User identity is propagated downstream
  Role policies are enforced
  Automated tests demonstrate all three

That changes the job of the coding system. The developer is no longer trying to write some plausible authentication code; the system is trying to make the observed software state satisfy these conditions. After implementation, the interesting output might be:

Build                 PASS
Unit tests            PASS
Integration tests     FAIL
Security checks       PASS
Architecture checks   PASS

That failed integration test is not simply an error message. It is evidence that the desired state has not yet been reached, so the loop continues.

The missing piece: engineering memory
#

This creates another problem: how does each agent understand the software system? Today most coding agents reconstruct context repeatedly from source files, README files, architecture notes, Git history, search results, the current prompt and whatever still fits in the context window. This works remarkably well, but much of the system model remains implicit, and every agent is effectively rebuilding its own partial understanding of the codebase.

That is where I think a knowledge graph becomes interesting — not simply a graph of code, but an engineering knowledge graph.

Beyond a code graph
#

A code graph might tell us that AuthController CALLS AuthService. Useful, but relatively low-level. What I want the graph to represent is the chain between business intent and observable engineering evidence.

flowchart TD
    R[Requirement]
    C[Capability]
    S[Service / Component]
    CODE[Code]
    ADR[Architecture Decision]
    T[Test]
    E[Evidence]

    R -->|SATISFIED_BY| C
    C -->|REALISED_BY| S
    S -->|IMPLEMENTED_BY| CODE

    S -->|CONSTRAINED_BY| ADR

    R -->|VERIFIED_BY| T
    T -->|PRODUCES| E

Other relationships can sit alongside these:

Component DEPENDS_ON Component
API EXPOSES Capability
Change MODIFIES Component
Incident CAUSED_BY Component
Test VERIFIES Requirement
ADR CONSTRAINS Component

Now an agent is not simply navigating files; it can reason over a model of the engineering system.

The Architect becomes an owner of desired graph state
#

This changes the role of the Architect agent quite significantly. Instead of merely producing a plan, the Architect can define the desired graph transformation. Imagine asking: “Add Xero integration.” The system may currently know:

Financial Reporting
 ├── Bank data
 ├── Donations
 └── Budgeting

The desired state may be:

Financial Reporting
 ├── Bank data
 ├── Donations
 ├── Budgeting
 └── Xero Integration
       ├── OAuth lifecycle
       ├── Tenant mapping
       ├── Account mapping
       ├── Transaction import
       └── Reconciliation rules

The engineering task then becomes:

flowchart LR
    A[Current Graph] --> B[Desired Graph]
    B --> C[Delta]
    C --> D[Implementation]
    D --> E[Evidence]

That is a much stronger abstraction than simply generating an implementation checklist.

Explorer becomes the graph hydrator
#

The Explorer agent then has another responsibility: keep the graph aligned with reality. Some relationships can be discovered deterministically — imports, function calls, package dependencies, API routes, database schemas, Terraform resources, CI/CD pipelines and tests. Others require inference.

For example:

TrusteeService
    IMPLEMENTS
Trustee Eligibility

That second relationship is not necessarily visible directly in an AST or import graph. An LLM may infer it from names, usage, documentation and surrounding code, and that distinction matters. I would therefore attach provenance to graph assertions.

{
  "from": "svc:trustee-service",
  "type": "IMPLEMENTS",
  "to": "cap:trustee-eligibility",
  "source": "explorer",
  "provenance": "src/services/TrusteeService.ts",
  "confidence": 0.91
}

The graph should never pretend that an AI inference and a compiler-derived relationship have the same status.

Different kinds of truth
#

This leads to an important separation: the LLM is not the source of truth, and neither is the graph. I find it useful to think of the system as having several different forms of memory and evidence.

flowchart LR
    L[LLM Context
Working Memory]
    G[Knowledge Graph
Engineering Memory]
    V[Git
Historical Record]
    R[Runtime & Tests
Observed Reality]

    L <--> G
    G <--> V
    G <--> R

LLM context is working memory, the graph is structured engineering memory, Git records what actually changed, and runtime behaviour and tests provide evidence about what is actually true. That means the AI reasons over truth rather than owning truth, and I think this is a critical architectural principle for agentic systems generally.

Making the graph practical locally
#

The next question is less philosophical: where does the graph actually live? My preferred approach is to avoid making the graph database itself the authoritative store. Instead, I would treat Git as the durable source of truth for the semantic engineering model and use a graph database as a fast materialised projection.

flowchart LR
    GIT[Git Repository]
    JSON[Canonical Graph Files]
    LOAD[Graph Loader / Reconciler]
    DB[FalkorDB]
    AGENTS[OpenCode Agents]

    GIT --> JSON
    JSON --> LOAD
    LOAD --> DB
    DB --> AGENTS

    AGENTS -->|semantic updates| JSON

That gives two useful properties at once: the graph remains diffable, reviewable, versioned and branch-aware, while agents still get fast graph traversal rather than repeatedly parsing flat files.

I would not use one giant JSON file
#

A single graph.json looks appealing initially, but it will become difficult to review very quickly. I would instead use JSONL and separate the different kinds of knowledge.

graph/
├── schema.yaml
├── authored/
│   ├── requirements.jsonl
│   ├── capabilities.jsonl
│   ├── architecture.jsonl
│   └── relationships.jsonl
│
├── inferred/
│   └── semantic-relationships.jsonl
│
└── generated/
    ├── imports.jsonl
    ├── routes.jsonl
    ├── dependencies.jsonl
    └── tests.jsonl

This separation matters because these files represent different kinds of authority.

flowchart TD
    A[Authored Knowledge]
    B[Deterministically Generated Knowledge]
    C[AI-Inferred Knowledge]
    D[FalkorDB Runtime Graph]

    A --> D
    B --> D
    C --> D

Authored knowledge includes requirements, ADRs and intentional relationships and should generally be committed. Generated knowledge includes relationships that can be deterministically rediscovered from source, so there is less value in permanently duplicating all of that in Git. Inferred knowledge may be worth persisting, but only with provenance and confidence.

Why FalkorDB becomes a projection
#

This is why I would treat something like FalkorDB as a runtime projection rather than the system of record. At startup:

flowchart TD
    A[Start local environment]
    B[Start FalkorDB]
    C[Load authored graph]
    D[Analyse repository]
    E[Generate deterministic relationships]
    F[Load retained inferred knowledge]
    G[Reconcile graph]
    H[OpenCode ready]

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F
    F --> G
    G --> H

The first version can be simpler still: start FalkorDB, reload the graph and go. For a single local development environment, rebuilding the graph is unlikely to be particularly expensive, and later the process can become incremental.

Put a small abstraction in front of the graph
#

I also would not expose the database directly to every agent. Instead I would introduce something like:

graphctl init
graphctl hydrate
graphctl reconcile
graphctl query
graphctl validate
graphctl export

That gives the agent system a stable interface. The Architect might ask graphctl query capability authentication, Explorer might record a relationship through graphctl add-edge, and Reviewer might ask for constraints affected by the current HEAD. The important point is that the implementation underneath can evolve; FalkorDB today could become something else later without rewriting every agent prompt or tool integration.

Persistent changes should still flow through Git
#

There is one rule I would keep fairly strict: agents should not freely mutate the graph database and leave the result there. Persistent semantic knowledge should flow back into version-controlled files.

flowchart LR
    A[Agent]
    B[graphctl]
    C[Canonical JSONL]
    D[Git Diff]
    E[FalkorDB Projection]

    A --> B
    B --> C
    C --> D
    C --> E

That means a code change might produce a Git diff containing all of this together:

src/auth.ts
tests/auth.test.ts
graph/requirements.jsonl
graph/relationships.jsonl

The engineering model changes alongside the implementation. That feels important; otherwise we have simply created a second, invisible repository inside a database.

The graph makes debugging narrower
#

One of the most useful outcomes is that failures become easier to contextualise. Imagine simply being told that Test T92 failed. Without structured context, the coding agent may need to explore a large part of the repository. With a graph it can traverse:

flowchart TD
    T[Test T92]
    R[Requirement R127]
    C[Capability C14]
    S[Service S7]
    CH[Recent Change]

    T -->|VERIFIES| R
    R -->|SATISFIED_BY| C
    C -->|IMPLEMENTED_BY| S
    CH -->|MODIFIED| S

The prompt to the agent can now become: “T92 verifies requirement R127. R127 is implemented primarily by S7 and S9. S7 changed in the latest commit and T92 began failing after that change. Determine whether the implementation or the test is inconsistent with R127.”

That is a far more bounded reasoning problem and much closer to how experienced engineers actually debug.

The agents become responsibilities, not necessarily models
#

At this point, I would describe the system in terms of six responsibilities rather than six separate models.

Architect — intent: maintains requirements, architecture decisions, constraints and desired graph transformations.
Explorer — understanding: hydrates and validates the graph against the repository.
Developer — action: changes code, infrastructure and configuration.
Verifier — observation: executes deterministic checks.
Reviewer — judgement: evaluates whether the evidence satisfies the intended state and whether architectural constraints have been respected.
Documenter / Curator — memory: updates documentation and maintains long-term engineering context.

Around these sits an orchestrator:

while desired_state != evidenced_state:
    determine_next_action()
    execute()
    collect_evidence()
    update_graph()
    evaluate_difference()

Obviously, I would never make that an unconstrained loop. It needs cost boundaries, iteration limits, permissions and clear escalation points, but as a conceptual model it captures the behaviour I want.

Start smaller than the architecture diagram suggests
#

It would be very easy to turn this into a platform project, and that would probably be a mistake. My first implementation would be deliberately narrow: a graph schema, authored nodes and relationships stored as JSONL, FalkorDB running locally, a small graphctl utility, static extraction for modules/imports/tests, agent instructions to query the graph before broad repository exploration, and explicit write-back rules for useful semantic discoveries.

Then prove one loop.

flowchart TD
    A[Architect creates requirement]
    B[Requirement enters graph]
    C[Developer changes source]
    D[Explorer updates relationships]
    E[Verifier runs tests]
    F[Evidence enters graph]
    G[Reviewer evaluates state]
    H{Satisfied?}

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F
    F --> G
    G --> H

    H -- No --> C
    H -- Yes --> I[Complete]

Only after that would I start thinking about embeddings, GraphRAG, automatic ontology evolution or more elaborate multi-agent orchestration.

The bigger idea
#

What I find interesting is that this is starting to look very similar to the architecture I keep arriving at when thinking about enterprise AI. In the enterprise context: ontology + context + deterministic systems + AI reasoning + agents + memory. In a software engineering environment: software graph + deterministic tools + AI reasoning + specialist agents + Git history. They are really expressions of the same principle.

AI should not own truth. It should reason over a structured representation of truth, act through controlled mechanisms, observe the result, and continuously reconcile its model with reality.

That may turn out to be more important than simply giving coding agents ever larger models or ever larger context windows. The interesting evolution is not just from coding assistant to coding agent; it is from coding agent to engineering system.
